## 首页「接口连上了但没拿到内容 / jar 下载失败」二次修复

用户清空重装后依旧是空首页，错误文案 `jar 下载失败：服务器没有返回数据`
（= `convertResponse` 返回 null = 读到一半 IOException）。

### 判断
旧实现用全局 OkGo 下 spider jar，三处不适合 1MB 二进制：
- `readTimeout` 只有 10s（OkGoHelper.DEFAULT_MILLISECONDS）
- 允许 h2，部分蜘蛛站传大文件会 RST
- 断了只能从 0 重来（无 Range 续传）

### 改动
- 新增 `com.pigtv.api.JarFetcher`（手机版 + 电视版各一份，代码一致）
  - 独立 OkHttpClient：30s 读超时 / 强制 HTTP_1_1 / Range 续传 / `Accept-Encoding: identity`
  - 4 轮尝试，识别「返回的是网页（拦截页）」并摘一段文字
  - http 失败或拿到网页时自动换 https 重试一次
- `ApiConfig.loadJar` 重写：缓存命中直接用；md5 不符时**先降级跑旧包**再后台换新；
  下载结果先 `JarLoader.load()` 验证，能加载才替换缓存（md5 写错也能用）；
  下载放独立线程 + `JAR_DL_LOCK` 单飞，回调 post 到主线程
- `ApiConfig.getJarDiag()`：每轮尝试的状态码/字节数/异常，经 PhoneBridge 的 `jarDiag`
  传到前端空态（`.errDiag` 三行小字 + 「复制详情」→ 新增桥方法 `copyText`）
- 首页 `loadAll` 加 9 秒慢加载提示「正在准备播放组件…」，避免冷启动时误显示「没有内容」
- `ensureJarBlocking`：JAR_MAX_TRY 1（重试交给 JarFetcher，避免抢 .part），等待 60s

### 产物（dist/，tv-release.jks / tvbox123456，CN=TVBox 与旧包一致可覆盖安装）

## 轮次 4：切线路后首页左上角站名不变

### 根因（不是 UI 忘了刷，是结果串台）
`SourceViewModel.sortResult` 只有**一条** LiveData，`PhoneBridge.sortCb` 只有**一个**槽，
「谁在等结果」和「结果是谁请求的」结构上对不上号。切换时必然撞车：

1. 旧站点 A 的 `getSort` 还在飞（spider 慢，type=3 还有 20 秒超时兜底）；
2. 用户切到 B → `setSite` 清掉 sortCb、再 `config()` 重新挂上 cbId_B；
3. A 的结果这时才到 → 落到 cbId_B 上 → 前端把 A 的配置当成 B 的
   （左上角站名是 A 的，首页内容也是 A 的）；
4. B 的真结果回来时 sortCb 已被消费 → 直接丢 → B 的首页永远空。

另外 `loadAll()` 里写 `#srcName` 只在 config 回调里，而 config 要先
`ensureJarBlocking(12s)` 再等站点返回，快则几秒慢则几十秒 —— 这段时间一直挂旧名字，
用户看到的就是「切了没反应」。

### 改动
- `SourceViewModel`：加请求代数 `sortGen`。每次 `getSort` 领一个，只有当前代数的结果
  才准 `postSort` / `cacheSort`；新增 `cancelSort()`（换源时作废在飞请求 + 清 sortCache）。
  另加 `sourceBean == null` 保护（换接口后残留的旧 sort id 会 NPE）。
- `PhoneBridge.config()`：加 35 秒看门狗 `armSortWatchdog`，`sortCb` 一直没被消费就自己
  回一条错误，前端不会永远停在空态。
- `PhoneBridge.resetSourceCaches()`：调 `vm.cancelSort()`。
- 前端：新增 `applySourceName(name)`（空值不覆盖，同时刷 `#srcName` + `#siteHint`），
  在 `pickSite` / `pickApi` / 保存接口三处**先用回包落一次**，不再等 config；
  `loadAll` 里的两处直写改成走 `applySourceName`。
- TV 版 `SourceViewModel` 整段同步（只编译验证，按用户要求不打包）。

### 验证
- 新增 `ui-design/_verify_srcname.js`（10 条断言，故意让 config 慢 900ms 复现空窗期）
- `_verify_switch.js` 18/18、`_verify_app.js` 181/181、srcname 10/10，零 JS 错误
- 重出 `dist/猪猪影视-手机版-universal.apk`(46M) / `-arm64.apk`(29M)，v1+v2+v3 校验通过

## 轮次 5：首页空 = 组件只下到 256/1024KB 就被放弃

### 真因（截图一句话说明白）
`JarFetcher.MAX_ATTEMPT = 4`，而源站**每次连接只给六七十 KB 就 RST**
（详情里 4 条全是 `SocketException: Connection reset`）。
4 × 64KB = 256KB → 老代码判定失败收工。**每次重连其实都有净进度**，
不是下不动，是「放弃得太早」。更糟的是 `ApiConfig` 失败时还 `r.file.delete()`
把 256KB 的残包删了，下一轮又从 0 开始 —— 慢网永远追不上。

### 改动
- `JarFetcher`：改成**分段续传**。某次只拿到 N 字节就断 → 下一轮只请求 N 字节
  那么长的一段（`Range: bytes=a-b`），请求段短了连接就能在被打断前正常结束，
  于是每轮必有净进度。重试次数改成按「有没有进展」算（连续 10 次零进展才停），
  总时长 210 秒兜底，退避最大 3 秒；加 `Connection: close`（别落到池里的死连接）。
- `JarFetcher.Progress` → `PhoneBridge.bindJarProgress()` → `window.__evt('jar', ...)`
  → 首页显示「正在下载播放组件 312/1024KB」。**这是本轮体验上最关键的一条**：
  以前几十秒白等，用户以为卡死。
- `ApiConfig.loadJar`：残包**保留**（原来会删），跨天残包才丢（防站点换包拼坏）。
- `PhoneBridge`：`config()` 等 jar 从 12s → 30s；失败且「残包保留」时
  45 秒后台自动续传一轮，成功推 `{'done':1}`，前端自己 `loadAll()`。
- 前端：`onJarProgress()`/`__evt`、`renderHero` 空态优先显示进度、
  切 Tab 回来不丢、有内容后进度事件不再抢戏。

### 关于「把文件夹名改回 tvbox」
不是原因，且**改了也没用**：工程目录名不进编译产物（`grep -c pig-tv` 在 APK 里 = 0，
`settings.gradle` 只有 `rootProject.name`，无路径依赖）；
`grep -rn "com\.tvbox"` 在整个 phone 源码里 = 0，改名是干净的。
运行时身份是 `applicationId com.pigtv.phone`，跟网络无关。

### 验证
- 新增 `ui-design/_verify_jarprog.js` → 10/10
- 回归：`_verify_app.js` 181/181、`_verify_switch.js` 18/18、`_verify_srcname.js` 10/10
- 两个 APK 重签，证书 SHA-256 `891467de462f…`（可覆盖安装）
- **本机无法复现源站**：`http://肥猫.live` 所有路径都返回 11.5KB「警告」页，
  只有用户手机的网络能过 —— 所以这条只能靠用户实测确认。

### 取证方法与结论
- 对 93cc210 的 585 个文件逐个做「包名归一化后再比对」：**0 处无法用包名替换解释的逻辑改动**
  （脚本报的 9 处是我替换顺序造成的假阳性 + README 文案 + 新增 room schema）。

  编译期解析，运行期类名不变。
- **`com.github.catvod.net.OkHttp` 在改名前的旧包（dist/猪猪影视-手机完整版-通用.apk，10-21 21:11）
  dex 里出现 0 次**，`androidx/base` 4209 次；当前包（加了 keep）是 3 次。
  → 混淆改名这件事**跟 tvbox→pig-tv 完全无关**，从第一次构建就存在。
- 上游 `box-main.tar.gz` 的 app/build.gradle **没有 minifyEnabled**（不混淆），
  而本 fork 从 init 起就是 `minifyEnabled true` + `-repackageclasses androidx.base`
  + 只 keep `com.github.catvod.crawler.*`。
- 工程目录名不进产物：APK 里 `pig-tv` 计数 0，dex 里 `pig-tv-phone` / `Box-phone` 均 0。
  **把文件夹改回 tvbox 不会有任何变化。**

### 为什么"改名后才开始失败"是真的、但原因不是依赖
applicationId 从 `com.github.tvbox.osc.tk.phone` 变成 `com.pigtv.phone` →
`getFilesDir()` 整个换成新目录 → 旧的 `csp/*.jar` 缓存、Hawk 配置、接口列表全部作废。
等于每次都是冷启动，每次都走一遍「重新下载 spider jar」，于是把下面两个老毛病全暴露出来：

| 老毛病 | 位置 | 起始时间 |
|---|---|---|
| R8 把 `catvod.net.OkHttp` 改成 `androidx.base.xxx`，jar 一调就 NoClassDefFoundError | proguard 只 keep `crawler.*` | 从 init 第一次构建就有 |
| jar 下载用全局 OkGo：10s 超时、无重试、无 Range、下载前先删旧包、失败拿半截包去 load | `ApiConfig.loadJar` 原版 | 从 init 就有 |

### 原版 loadJar 的四处硬伤（原样记录，便于以后解释）
1. `OkGo.getInstance()` 全局 client，`DEFAULT_MILLISECONDS = 10000`（OkGoHelper 第 39 行）。
2. 一次请求定生死，没有重试、没有 `Range` 续传。
3. `if (cache.exists()) cache.delete();` —— 下载前先删缓存，下挂了就啥也不剩。
4. `onError` 里 `if (cache.exists()) jarLoader.load(cache)` —— 拿半截 jar 当完整 jar 加载。

## 轮次 7：与上游 takagen99/Box 逐段对比首页加载

### 上游（HomeActivity.initData，两 bit 状态机 + 重入）
```
initData()
├ isNetworkAvailable → 设 wifi/4G 图标
├ if (dataInitOk && jarInitOk) → getSort(homeKey); return
├ showLoading()
├ dataInitOk && !jarInitOk → loadJar(...)
│     success → jarInitOk=true → 50ms 后 initData()
│     error   → jarInitOk=true, dataInitOk=true → 50ms 后 initData()   ← 失败照样往下走
└ else → loadConfig(...)
      success → dataInitOk=true（spider 空则 jarInitOk=true）→ 50ms 重入
      error "-1"（没配置）→ 两个都 true → 重入
      error 其它 → TipDialog；点取消也把两个 flag 置 true 重入
```
特点：**每一步回调里再调一次 initData()，靠 flag 推进，任何一步都不阻塞线程**；
jar 失败不阻断，type=0/1 的 JSON/XML 站点照样出内容，只有 type=3 才空。
换源走 `showSiteSwitch() → setSourceBean() → reloadHome()`，
`reloadHome()` 用 `FLAG_ACTIVITY_CLEAR_TASK` **重启整个 Activity**（useCache=true），
所以上游不存在「旧请求的新结果落到新站点上」这种串台。

### 我们（index.html loadAll → PhoneBridge.config）
```
loadAll() → ncall('config')
└ PhoneBridge.config()（线程池）
   ├ home 无 api → needConfig=1
   ├ ensureJarBlocking(30000L)        ← 阻塞
   ├ sortCb=cbId; vm.getSort(key); armSortWatchdog(35s)
   └ sortResult observer → cb(cbId, {ok,sorts,rec,source,jarError,diag})
```

### 对照出来的真 bug
`ensureJarBlocking` 里 `latch.await(Math.max(maxWaitMs, JAR_WAIT_MS))`，
而 `JAR_WAIT_MS = 60_000L`、调用处传 30_000L → **实际等 60 秒**，注释写的是 30 秒。
再加上 35 秒看门狗，冷启动最坏 60+35=95 秒才有反馈。上游这一段是 0 等待。

### getSort 与上游的差异（只有三类，没删逻辑）
1. `sortGen` 代数校验（`postSort` / `cacheSort`）
2. `sourceBean == null` 保护（上游直接 `sourceBean.getType()` 会 NPE）
3. `SpiderDiag` 记录失败原因（上游只有 `printStackTrace`）

### 结论
上游靠「Activity 重建」换取状态干净；WebView 版没有这个手段，
所以必须自己补代数校验/取消/看门狗 —— 这解释了为什么同样是 TVBox 的血统，
手机版这边换源和冷启动的问题比上游多。

## 轮次 8：按上游思路改「首页等 jar」并出包

### 改动（pig-tv-phone / PhoneBridge.java）
1. **真 bug 修正**：`latch.await(Math.max(maxWaitMs, JAR_WAIT_MS))` → `latch.await(maxWaitMs)`。
   原来传 30s 实际等 60s（JAR_WAIT_MS=60000），与注释不符。顺带把 category 的 15s、
   detail 的 20s 也真正生效（之前都被抬到 60s）。
